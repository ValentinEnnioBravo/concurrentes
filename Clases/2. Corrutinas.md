# Corrutinas
Hasta ahora trabajamos sobre un modelo de concurrencia basado en un event loop. En este esquema, cada evento se procesa completamente antes de pasar a la ejecución del próximo, y todo esto ocurre en un único thread. La E/S corta el proceso.

El **event loop** de JavaScript permite manejar muchas tareas sin bloquear el hilo principal: cuando JS inicia algo asíncrono (como una petición HTTP, un `setTimeout` o una operación de I/O), delega esa tarea al entorno (browser/Node.js) y sigue ejecutando; cuando la operación termina, el entorno **pone un callback/evento en una cola**, y el event loop va revisando esa cola y ejecuta los callbacks cuando el *call stack* está libre. Por eso JS normalmente no necesita **mutex** para coordinar estas tareas: en vez de varios hilos compitiendo por memoria al mismo tiempo y bloqueándose con locks, el modelo habitual es **un solo hilo ejecutando una cosa a la vez**, y las notificaciones de que algo terminó llegan mediante **eventos/callbacks/promesas** que el event loop procesa.

El event loop llama a epoll_wait() (Linux) y se bloque ahí, sin gastar CPU. El SO sabe por hw cuándo llegan datos y marca ese file descriptor como "listo". epoll_wait() se despierta y devuelve la lista de descriptores listos, el event loop de Python toma esa lista y reanuda la corrutina(que veremos más abajo).

Una ventaja que esto implica es que cuando una función se está ejecutando, tenemos la seguridad de que no va a ser interrumpida por el planificador hasta que termine, lo cual evita los problemas de concurrencia tradicionales que habíamos visto al usar threads y locks. Y esto lo logramos gracias a que el event loop le provee un orden a la ejecución concurrente; la serializa.

Las corrutinas nos permiten lograr algo similar, sin utilizar (necesariamente) un event loop.

## Ejemplo crawler
Un crawler es una estructura de datos, un componente de software o una característica de lenguaje diseñada para optimizar la velocidad de acceso y búsqueda de información, reduciendo la complejidad temporal de las operaciones. **Problema: mantiene muchas conexiones abiertas y realiza pocos cálculos**.

Al conectarse via socket: 
```py
def fetch(url):
    sock = socket.socket()
    sock.connect(('bla.com', 80))
    request = 'GET {} HTTP/1.0\r\nHost: bla.com\r\n\r\n'.format(url)
    sock.send(request.encode('ascii'))
    response = b''
    chunk = sock.recv(4096)
    while chunk:
        response += chunk
        chunk = sock.recv(4096)

    parse_response(response)
```

**Si se crea un hilo por cada request (solicitud), a medida que aumente el número de requests simultáneas, aumenta la posibilidad de quedarse sin memoria (cada hilo pesa 50KB) antes de que se agoten los sockets.** 

En sí un hilo pesa más que un socket, y esa diferencia es la motivación de las **corrutinas en vez de un hilo por conexión**.

Por defecto, las operaciones con sockets son bloqueantes, cuando el hilo llama a un método como connect o recv, se detiene hasta que la operación se completa. En consecuencia, para descargar muchas páginas a la vez, necesitamos muchos hilos (lo cual suele ser resuelto con pools de hilos o sockets).

Los hilos en Python tienen el GIL encima, aunque tengas 50 hilos solo uno ejecuta bytecode a la vez, liberan el GIL con I/O mientras esperan (ej: con el socket) pero no te dan paralelismo real de CPU.

## Async

```py
from selectors import DefaultSelector, EVENT_WRITE

selector = DefaultSelector()

# Falla aproposito
sock = socket.socket()
sock.setblocking(False)
try:
    sock.connect(('bla.com', 80))
except BlockingIOError:
    pass

# Pide aviso
def connected():
    selector.unregister(sock.fileno())
    print('connected!')

selector.register(sock.fileno(), EVENT_WRITE, connected)

def loop():
    while True:
        events = selector.select()
        for event_key, event_mask in events:
            callback = event_key.data
            callback()
```

Los frameworks de E/S asincrónicos realizan operaciones simultáneas en un solo hilo utilizando sockets no bloqueantes. Un socket no bloqueante genera una **excepción** (EINPROGRESS errno) al realizar el `connect`, incluso cuando funciona normalmente. Python lanza BlockingIOError de inmediato en vez de esperar. No es un error real, es el equivalente a "ya arranqué el handshake, seguí con lo tuyo". Por eso se ignora con pass.

Luego se le dice al selector "avisame cuando este socket purda escribir". Un socket TCP se vuelve "escribible" cuando el handshake termina y ya podés mandar datos. Entonces EVENT_WRITE es, en la práctica, la señal de "conexión establecida". Registrás el fd + qué evento te interesa + qué función llamar (connected) cuando pase.

`selector.select()` internamente es `epoll_wait()`. Se duerme hasta que el kernel le avisa que algún fd registrado está listo. Cuando despierta, te da la lista de eventos listos, y se ejecutá el callback asociado a cada uno.

**Todo esto corre en un solo hilo**. Si tuviera 1000 sockets conectando a la vez, el mismo loop los atiende a todos, uno por uno, a medida que cada uno avisa que está listo — nunca dos cosas ejecutándose en el mismo instante literal. Eso es concurrencia (superponer esperas de I/O). Paralelismo sería usar varios núcleos para hacer cálculos simultáneos de verdad, que es otro problema (CPU-bound), y este sistema no lo resuelve.

## Corrutinas
### Generadores
Es un tipo de subrutina, un subconjunto de corrutina, es una función que produce una secuencia de resultados en lugar de un solo valor.

### Iteradores
Es un objeto que permite recorrer un contenedor (colección de elementos). Una manera de implementarlos es utilziando, **generadores**, que puede producir valores para quien lo llama varias veces (en lugar de devolver solo uno).

#### Ejemplo
```py
def cuenta_regresiva(numero):
    while numero > 0:
        yield numero
        numero -= 1

for numero in cuenta_regresiva(5):
    print(numero)

# El resultado de ejecutar el script es: 5 4 3 2 1
```
`yield` devuelve un valor a quien llamo a `next()`, pausa la funciòn congelando su estado hasta que alguien vuelva a pedir su valor, a dif del return que corta la funcion y borra el estado.

El **generador** es el objeto que guarda el estado pausado de la función y sabe cómo reanudarla. Cuando llamás a una función con yield, Python no ejecuta nada todavía: crea un generador, que es como una "cápsula" con la ejecución congelada en el punto de partida, esperando el primer `next()`.

El **iterador** es la interfaz estándar para recorrer secuencias, un elemento a la vez, bajo demanda (implementa `__next__()`). El for, las comprensiones, list(), etc., todos usan este protocolo sin saber nada de generadores en particular. yield es la palabra clave que convierte una función en fábrica de generadores. El generador es un tipo concreto de iterador.

Con una función común, cuando termina (con `return` o al llegar al final), Python destruye su *stack frame*: variables locales, posición del puntero de instrucción, todo se pierde.

Con un generador, ese frame vive en el **heap** (memoria persistente), no en el stack. Entonces cuando llega al `yield`:

1. `cuenta_regresiva(5)` crea el generador (frame nuevo, `numero=5`, aún sin ejecutar nada).
2. El `for` internamente hace `next(gen)`:
   - Entra al frame, `numero=5`, `while` se cumple, llega a `yield numero` → devuelve `5`, **congela el frame ahí mismo**.
3. `for` asigna `numero_del_for = 5`, ejecuta `print(5)`.
4. `for` pide el siguiente valor → `next(gen)`:
   - Python **no vuelve a entrar por arriba de la función**. Va directo al frame guardado, retoma justo **después** del `yield` anterior.
   - Ejecuta `numero -= 1` → ahora `numero=4` (mismo frame, misma variable, no una nueva).
   - El `while` vuelve a chequear (`4 > 0`, sí), llega otra vez a `yield numero` → devuelve `4`, congela de nuevo.
5. Se repite así hasta `numero=0`: el `while` ya no entra, la función llega a su fin natural → se lanza `StopIteration`, el `for` lo capta y termina el loop (sin error visible para vos).

No es que "se le pasa el número al for y el for se lo devuelve". El `for` solo recibe el valor devuelto por `yield` y lo usa (`print`). La variable `numero` **nunca sale de la función** `cuenta_regresiva`: vive en su frame, que persiste en memoria entre llamadas a `next()` porque el generador lo retiene, exactamente como una función pausada con un "bookmark" en el punto donde se quedó.

###  El concepto de Corrutinas
Una corrutina es similar a una subrutina tradicional (funciones/procedimientos de algs.) pero con la diferencia de que, mientras que **la salida de una subrutina pone fin a su ejecución**, **una corrutina puede además suspenderse, cediendo el control a otra** hasta que se le indique que debe retomar su ejecución.

#### Sin corrutinas 
```py
import time

def io():
    time.sleep(1)
    print('1')
    time.sleep(1)
    print('2')
    time.sleep(1)
    print('3')

def main(tareas):
    for tarea in tareas:
        io()

if __name__ == '__main__':
    tiempo = time.perf_counter()
    main(range(3))
    tiempo2 = time.perf_counter() - tiempo
    print(f'Tiempo total: {tiempo2:0.2f} segundos')

# Esto imprime 1 2 3 1 2 3 1 2 3 Tiempo total: 9.01 segundos
```
Podemos ver que cada ciclo de IOs de cada tarea se ejecuta y termina una atrás de la otra. ¿Qué pasa si agregamos corrutinas?

#### Con corrutinas
```py
import time
import asyncio

async def io():
# Hay un async adelante del def, asi que soy una corrutina :D
    await asyncio.sleep(1)
    print(1)
    await asyncio.sleep(1)
    print(2)
    await asyncio.sleep(1)
    print(3)

async def main():
    await asyncio.gather(io(), io(), io())

if __name__ == '__main__':
    tiempo = time.perf_counter()
    asyncio.run(main())
    tiempo2 = time.perf_counter() - tiempo
    print(f'Tiempo total: {tiempo2:0.2f} segundos')
# 1 1 1 2 2 2 3 3 3 Tiempo total: 3.00 segundos. La diferencia de tiempos y el orden de ejecución es distinto.
```
`asyncio.gather(io(), io(), io())` Crea 3 corrutinas `io()` y las lanza **todas al event loop en paralelo (concurrentemente)**, no una después de la otra. `gather` espera a que las 3 terminen antes de devolver el control a `main()`.

**Traza de ejecución**
1. Arrancan las 3 corrutinas casi al mismo tiempo (t=0).
2. Cada una llega a `await asyncio.sleep(1)` y se **pausa**, devolviendo el control al event loop (no bloquea nada, solo dice "avisame en 1 segundo").
3. Como las 3 durmieron al mismo tiempo, el event loop las despierta a las 3 casi juntas, a t≈1.
4. Cada una imprime `1` (en algún orden, probablemente las 3 seguidas) y vuelve a hacer `await asyncio.sleep(1)`.
5. A t≈2 se despiertan las 3 de nuevo, imprimen `2`, vuelven a dormir.
6. A t≈3 se despiertan, imprimen `3`, y terminan.

Con `gather`, las 3 corrutinas comparten el mismo hilo pero **superponen sus esperas**: mientras una está "dormida" esperando su segundo, el event loop puede atender a las otras dos (o simplemente no hacer nada útil, porque todas están durmiendo igual).

Esto es la misma idea de concurrencia I/O-bound que vimos antes: **no hay paralelismo real** (un solo hilo, un solo núcleo trabajando), pero como el "trabajo" acá es solo *esperar*, podés esperar las 3 cosas a la vez sin costo extra (**se solapa la espera, la ejecución de código py es secuencial**). Si en vez de `sleep` fuera una tarea que usa CPU real (cálculo pesado), esto no ayudaría en nada, porque ahí sí hay que turnarse para usar el único hilo disponible.

#### ¿Cómo funcionan?
Cuando usamos corrutinas, no hay intervención del SO. Hay un sólo proceso, un sólo thread. Lo que ocurre es que las corrutinas liberan la CPU cuando están en "tiempo de espera" (await), permitiendo que otras puedan usar la CPU.

Podemos decir que es como una simultánea de ajedrez, en donde una persona juega contra dos o más. Hace un movimiento y no se queda esperando la respuesta del oponente en ese tablero, sino que pasa al siguiente y realiza un movimiento ahí. De esa forma, trata las partidas (tareas) de forma **concurrente**, lo que resulta en que se terminen en menos tiempo. Es decir; **hay concurrencia, no paralelismo**.

## Corrutinas vs. Threads
La diferencia fundamental entre corrutinas y threads se da en la forma en la que se lleva a cabo la multitarea.

Los **threads**, como ya vimos, manejan un esquema de **multitarea apropiativa** (en inglés, preemptive multitasking), donde el planificador es el encargado de asignar intervalos de uso de CPU a los threads que se están ejecutando, desalojándolos cuando este termina.

Las **corrutinas**, en contraposición, permiten tener m**ultitarea cooperativa** (cooperative/non-preemptive multitasking). Esto significa que el cambio de contexto no es controlado por el planificador, sino que cada corrutina es la encargada de ceder el control cuando está inactiva o bloqueda. Lo ceden con `await` (o `yield` si son generadores usados como corrutinas, a la vieja usanza pre-async/await).

Internamente ante un await:
1. Pausa ejecución de la corrutina
2. Devuelve el control al event loop junto con la info de "avisame cuando esté listo"
3. El event loop queda libre para atender otras corrutinas o esperar eventos.
4. Cuando la condución se cumple el event loop la retoma justo después del `await` (cmomo con `next()`en los generadores)

Otra diferencia, presente al menos en la visión "tradicional" de corrutinas, es que las corrutinas proveen **concurrencia pero no paralelismo**.

Sí, es un buen resumen porque muestra la progresión de menor a mayor control. Te la sintetizo para que quede aún más claro el hilo conductor:

### Ejemplo
```python
import asyncio

def print_loco(algo):
  return print(algo,'loco')

async def print_re_loco(algo):
  return print(algo,'loco')

# print_loco('bla')        → ejecuta inmediatamente, imprime
# print_re_loco('algo')    → NO ejecuta nada, devuelve un objeto corrutina pausado
```

Llamar a una función `async def` **no la corre** — solo crea el objeto corrutina (como vimos con los generadores: se crea el "paquete" congelado, listo para arrancar). Necesitás algo externo que la impulse.

**Las 5 formas, en una escalera de "quién controla qué"**

| Método | Qué hace | Cuándo usarlo |
|---|---|---|
| `asyncio.run(coro)` | Crea el event loop y corre **una sola** corrutina de punta a punta | Punto de entrada del programa (solo una vez, en el `main`) |
| `await coro` | Ejecuta la corrutina y **espera su resultado antes de seguir** | Cuando necesitás el resultado ya para continuar (secuencial) |
| `create_task(coro)` | Manda la corrutina al event loop **en background**, sin esperarla todavía | Cuando querés que arranque ya pero seguir haciendo otra cosa mientras tanto |
| `gather(c1, c2, ...)` | Corre varias corrutinas concurrentemente y **te devuelve resultados en una lista, en orden** | Cuando lanzás varias a la vez y te interesa el resultado de todas |
| `TaskGroup()` | Como `gather`, pero con **manejo de errores más prolijo** (si una falla, cancela las demás) y permite agregar tasks dinámicamente | Concurrencia estructurada, cuando querés garantías de que nada quede "suelto" |

- `await` es literalmente el "ceder el control" 
- `create_task` es lo que te permite tener **varias corrutinas pausadas al mismo tiempo**, compitiendo cooperativamente por el único hilo — de ahí que `gather(io(), io(), io())` del ejemplo anterior en realidad haga `create_task` internamente por cada una, para que las 3 puedan "estar en vuelo" a la vez en vez de una detrás de la otra.

#### `asyncio.gather()` vs `asyncio.TaskGroup`

Podemos pensarlo de esta forma:

- **`gather`**: "ejecutá estas cosas concurrentemente y dame sus resultados"
- **`TaskGroup`**: "estas tareas forman juntas una unidad de trabajo; si una falla, ocupate de cancelar correctamente las demás"

| Característica | `asyncio.gather()` | `asyncio.TaskGroup` |
|---|---|---|
| Ejecutar cosas concurrentemente | ✅ | ✅ |
| Obtener resultados | ⭐ Excelente | Hay que obtenerlos desde `Task` |
| Manejo de errores | Flexible | Estructurado |
| Cancela hermanas cuando una falla | ❌ No por defecto | ✅ |
| Structured concurrency | ❌ | ✅ |
| Ciclo de vida de tareas | Más flexible | Más controlado |
| Uso típico | "Necesito estos resultados" | "Estas tareas forman un trabajo" |

#### Reglas clave de la "Concurrencia estructurada"

- **Duración limitada**: los subprocesos o tareas no pueden sobrevivir al bloque de código o ámbito que los creó.
- **Jerarquía padre-hijo**: una tarea padre espera a que todas las subtareas hijas finalicen.
- **Propagación automática**: si una tarea hija falla o se cancela, las tareas hermanas se pueden detener automáticamente.

## ¿Qué pasa si ejecuto código bloqueante dentro de una corrutina?
Para suspender a la corrutina, se usa `asyncio.sleep` en lugar de `time.sleep`. Esto es porque el segundo es bloqueante. Entonces como ya dedujeron, las operaciones bloqueantes bloquean todo el thread del sistema operativo subyacente.

Pero hay formas de evitarlo :D!, lo que se hace es que correr estas tareas bloqueantes y otras que vamos a llamar CPU-bound-intensive, sea conveniente ejecutarlas en otro thread. Concretamente en Python usando `loop.run_in_executor()`.

## Corrutinas vs. Generadores
Si bien ambos pueden ceder múltiples veces, suspender su ejecución y permitir el reingreso en múltiples puntos de entrada, difieren en que las corrutinas tienen la capacidad para controlar dónde continúa la ejecución inmediatamente después de ceder, mientras que los generadores no pueden, estos transfieren el control de nuevo al generador que lo llamo.

Es decir, dado que los generadores se utilizan principalmente para simplificar la escritura de iteradores, la declaración de rendimiento en un generador no especifica una rutina para saltar, sino que devuelve un valor a una rutina principal.

## El Crawler refactorizado
### Con corrutinas basadas en generadores
```py
# Fetch como función generadora, Creamos un future pendiente, luego lo cedemos para pausar la búsqueda hasta que el socket esté listo.
def fetch(self, url):
        response = yield from self.session.get(url)
        body = yield from response.read()

# Pero cuando el future se resuelva, ¿qué reanuda el generador? Necesitamos un controlador de rutina. Llamémoslo "tarea":

class Task:
    def __init__(self, coro):
        self.coro = coro
        f = Future()
        f.set_result(None)
        self.step(f)

    def step(self, future):
        try:
            next_future = self.coro.send(future.result)
        except StopIteration:
            return

        next_future.add_done_callback(self.step)

fetcher = Fetcher('/333/')
Task(fetcher.fetch())

loop()
```

Task inicia el generador "fetch" enviando None. Luego, fetch se ejecuta hasta que produce (yield) un future, que la tarea captura como siguiente future. Cuando el socket está conectado, el event loop ejecuta el callback on_connected, que resuelve el future, que llama a step, que reanuda fetch.
