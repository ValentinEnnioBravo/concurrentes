# Clase 2: Event loop, CPS y corrutinas

En la clase 1 vimos que la forma tradicional de atender varias tareas es darle **un thread (o un proceso) a cada una**. Para tareas **IO bound** eso es un desperdicio: cada thread pasa casi todo el tiempo esperando la red o el disco, pero igual ocupa memoria y cambios de contexto.

Esta clase responde una pregunta: **¿se pueden atender muchísimas esperas de I/O con un solo thread?** El recorrido es:

1. El problema concreto (un crawler).
2. Las dos formas de repartir el procesador: apropiativa y cooperativa.
3. **CPS**: escribir el código como "qué hacer cuando termine".
4. El **event loop** de Node.js, que usa esa idea, y las **Promises**.
5. El mismo event loop armado a mano en Python, y por qué el código con callbacks se vuelve difícil.
6. **Generadores** y **corrutinas**: cómo pausar una función y retomarla después.
7. **asyncio** en la práctica, sus trampas y cómo se compara con los threads.

---

## 1. El problema: un crawler

Un **crawler** es un programa que descarga páginas web y sigue sus links para descargar más. Es el caso típico de una aplicación **IO bound**: mantiene muchas conexiones abiertas y hace muy pocos cálculos.

La versión ingenua descarga una página usando un socket:

```py
def fetch(url):
    sock = socket.socket()
    sock.connect(('bla.com', 80))            # bloquea hasta conectar
    request = 'GET {} HTTP/1.0\r\nHost: bla.com\r\n\r\n'.format(url)
    sock.send(request.encode('ascii'))
    response = b''
    chunk = sock.recv(4096)                  # bloquea hasta que lleguen datos
    while chunk:
        response += chunk
        chunk = sock.recv(4096)
    parse_response(response)
```

Por defecto las operaciones de sockets son **bloqueantes**: cuando el thread llama a `connect` o `recv`, se detiene hasta que la operación termina. Para descargar muchas páginas a la vez hacen falta muchos threads (o un pool de threads).

El problema: **cada thread pesa unos 50 KB** y el SO pone un tope a cuántos se pueden crear. Al aumentar las conexiones simultáneas, nos quedamos sin memoria (o sin threads) **antes que sin sockets**. Es el **problema C10K** (atender 10.000 conexiones a la vez). Un socket es mucho más barato que un thread, así que lo ideal sería **un solo thread que atienda muchos sockets**.

> En Python, además, los threads tienen un **GIL** (igual que MRI): aunque haya 50 threads, solo uno ejecuta bytecode a la vez. Lo sueltan mientras esperan I/O, así que sirven para solapar esperas, pero no dan paralelismo de CPU.

La salida es la **E/S asíncrona**: en vez de quedarse esperando, el programa arranca la operación, se dedica a otra cosa y vuelve cuando el SO avisa que hay datos. Para eso, el código tiene que poder **ceder el control** en vez de ser desalojado.

## 2. Dos formas de repartir el procesador

- **Planificación apropiativa (*preemptive*)**: el planificador del SO decide cuándo cada contexto usa el procesador y **lo puede desalojar en cualquier momento**, incluso en medio de una sección crítica. Es lo que pasa con los **threads**. De ese desalojo arbitrario salen el no determinismo, las condiciones de carrera y la inanición, y por eso hacen falta locks.
- **Planificación cooperativa (*non-preemptive*)**: cada contexto es responsable de **ceder el control** por su cuenta; nadie lo interrumpe desde afuera. Los cambios solo ocurren en **puntos visibles del código** (el fin de un callback, un `yield`, un `await`).

La planificación cooperativa tiene una ventaja enorme: mientras una función se ejecuta, **nadie la interrumpe hasta que ceda**, así que entre dos puntos de cesión no hay carreras ni hacen falta locks. Los dos mecanismos que la aplican son el **event loop** y las **corrutinas**. El primero se apoya en una forma particular de escribir código: el CPS.

## 3. CPS (Continuation Passing Style)

Hay dos maneras de escribir una función: el **estilo directo** (devuelve el resultado con `return`) y el **estilo de paso de continuaciones**, donde la función recibe un callback y le pasa el resultado.

```js
// Estilo directo
function succesor(n) { return n + 1; }
console.log(succesor(1));

// CPS
function succesorCont(x, continuacion) {
  continuacion(succesor(x));
}
succesorCont(2, (y) => { console.log(y) });
```

- A ese callback se lo llama **continuación**: es lo que se ejecuta *a continuación*, en algún momento después de calcular el resultado.
- La función CPS no solo calcula: también tiene el **control** del flujo. Decide **cuándo** (y cuántas veces) sigue el programa.
- El resultado **solo se puede usar dentro de la continuación**. Esto es un *code smell*, porque asume que la continuación ya se ejecutó:

  ```js
  var i1;
  succesorCont(0, (resultado) => { i1 = resultado; });
  console.log(i1);   // rompe el modelo: no sabemos si ya se ejecutó
  ```

- **CPS es fácil de introducir e imposible de abandonar** sin introducir bugs: una vez que una función es CPS, todo lo que usa su resultado también lo es. Resta flexibilidad, pero obliga a ser consistente. Las partes que no dependen del resultado (una multiplicación, por ejemplo) pueden seguir en estilo directo.

**¿Para qué sirve?** Darle el control a la función permite modelar computaciones:
1. **Con falla**: si no hay resultado, la continuación no se llama y el flujo se detiene (no es lo mismo que devolver `null`).
   ```js
   function inversa(x, cont) { if (x !== 0) { cont(1 / x); } }
   ```
2. **No determinísticas**: la continuación se puede llamar 0, 1 o muchas veces. `hijoDeVito(cont)` la llama una vez por cada hijo; el callback de `http.createServer` se llama una vez por cada request, y no sabemos cuántas van a llegar.
3. **Con excepciones**: se pasan dos continuaciones, una para el flujo normal y otra para el error.
4. **Asincrónicas**: la continuación se ejecuta **más tarde**, cuando termine una operación lenta. Es la que más nos interesa: **"cuando lleguen los datos, hacé esto"**.

Encadenar llamadas en CPS anida callbacks (`succesorCont(1, y => succesorCont(y, x => console.log(x)))`), y si además se manejan errores, el código se vuelve ilegible: el **callback hell**. Se puede aliviar componiendo funciones CPS o armando un *pipeline*:

```js
function componer(f, g) {
  return (x, cont) => g(x, (y) => f(y, cont));
}
const pipeline = (fs) => fs.reduce(componer);
pipeline([duplicar, inversa, siguiente])(2, imprimir);
```

### Ejemplo: transferencias bancarias
- **Estilo directo**: las transferencias se ejecutan en orden y la que no tiene fondos no se hace.
- **Con callbacks pero sin encadenar** (`puedeExtraer` responde con un `setTimeout` aleatorio, como un banco externo lento): los resultados cambian en cada corrida, porque la transferencia 2 arranca sin esperar a que termine la 1. **No se garantiza el orden.**
- **CPS completo**: `ejecutar(cont)` recibe la continuación y cada transferencia se lanza dentro de la continuación de la anterior. Siempre da lo mismo, aunque las demoras sean aleatorias.

```js
transferencia1.ejecutar(() => {
  transferencia2.ejecutar(() => {
    transferencia3.ejecutar(() => console.log({ cuentaA, cuentaB }));
  });
});
```

Con continuaciones asincrónicas, alguien tiene que guardarlas y llamarlas cuando corresponda. Ese alguien es el event loop.

## 4. El event loop de Node.js

### La idea
Cuando JavaScript inicia algo asíncrono (una petición HTTP, un `setTimeout`, una lectura de archivo), **delega la operación al entorno** (Node.js o el browser) y sigue ejecutando. Cuando la operación termina, el entorno **pone su callback (la continuación) en una cola**. El **event loop** revisa esa cola y ejecuta los callbacks de a uno, cuando no hay otra cosa ejecutándose.

- Todo corre en **un único thread**, y cada evento se procesa **completo** antes de pasar al siguiente: el event loop **serializa** la ejecución concurrente.
- Por eso JS normalmente **no necesita mutex**: no hay varios threads compitiendo por la memoria, sino uno solo que hace una cosa por vez y se entera de que algo terminó mediante **eventos/callbacks/promesas**.
- El event loop no opera con locks sino con **notificaciones**: espera a que el SO le avise qué evento está listo.

### Las piezas
Node.js corre JavaScript sobre el motor **V8** (los browsers usan V8 o SpiderMonkey), que combina intérprete y compilación JIT. Para ejecutar usa:
- **Heap**: donde se alocan variables, funciones y estructuras.
- **Call stack**: pila de las funciones que se están ejecutando. Como JS es monohilo, se procesa una cosa a la vez.
- **Callback queue**: cola de los callbacks de operaciones asíncronas que ya terminaron (`setTimeout`, I/O, HTTP).

Cuando el call stack está vacío, el event loop toma el primer callback de la cola y lo ejecuta. Un **evento** es una pequeña función que se va a ejecutar más adelante.

```js
let a = 0;
for (let i = 0; i < 10000; i++) {
  setTimeout(() => a += 1, 0);       // genera un evento: el callback va a la cola
}
setTimeout(() => console.log('Dentro:', a), 3300);   // 10000
console.log('Fuera:', a);            // 0: se ejecuta ya, los callbacks todavía están en la cola
```

`setTimeout(f, 100)` garantiza **como mínimo** 100 ms, no exactamente 100: si en el call stack hay un `while` largo, el callback espera a que termine. Por eso el resultado es **no determinístico**. (Para visualizarlo: <http://latentflip.com/loupe>.)

### Fases del loop
Primero se ejecuta el script principal (`index.js`): lo inmediato se ejecuta y los eventos (continuaciones, operaciones asincrónicas, I/O) se encolan. Después el loop cicla por fases:
1. **Timers** (`setTimeout`/`setInterval`): callbacks de timers vencidos.
2. **JS**: código del thread principal.
3. **I/O** (la "función unicornio" de la clase): avisos de que terminó algo del kernel o del thread pool.
4. **`setImmediate`**: eventos instantáneos.
5. **Close events**: limpieza de lo que ya se ejecutó. Si no queda nada pendiente, termina; si no, vuelve a empezar.

Cada programa de Node tiene **un solo event loop** y todo el ciclo corre en **un thread**, con una política de **no desalojo** del código JS.

### Código CPU intensive y offloading
Como nadie desaloja al código JS, un cálculo pesado o una llamada sincrónica **bloquea todas las fases**. Opciones:
- **Partitioning**: partir el cálculo en pedazos.
- **Offloading**: delegar al kernel o al thread pool.
- **Worker threads**: correr el trabajo pesado en otros threads sin bloquear el loop.

```js
// Sincrónico: ~6 s para 6 hashes, el loop queda congelado
pbkdf2Sync('pwd', 'salt', 100000, 512, 'sha512');

// Asincrónico: ~3 s, se delega a los worker threads de libuv
process.env.UV_THREADPOOL_SIZE = 6;
pbkdf2('pwd', 'salt', 100000, 512, 'sha512', () => console.log('Done'));
```

**libuv** es la librería que envuelve las llamadas bloqueantes como no bloqueantes, usando un thread pool por detrás y avisando por callback. Así Node hace E/S sin bloquearse aunque JS sea monohilo.

> **Un solo thread no elimina las carreras.** Si un callback lee un dato, lanza una operación asíncrona y otro callback modifica ese dato antes de que vuelva la continuación, el primero puede pisar el cambio. Lo que el event loop garantiza es que **dentro** de un callback nadie interrumpe; **entre** callbacks, cualquier cosa puede pasar.

## 5. Promises

Las Promises son la forma de escapar del callback hell sin dejar de ser asíncronos.

Una **Promise** representa un valor que todavía no existe: el resultado futuro de una operación asíncrona. Está en uno de tres estados: **pendiente**, **cumplida** (*fulfilled*) o **rechazada** (*rejected*), y una vez resuelta no cambia.

- En lugar de pasarle la continuación a la función, la función **devuelve** la promesa y la continuación se engancha después con `.then(...)`; los errores, con `.catch(...)`.
- `.then` devuelve otra promesa, así que las operaciones se **encadenan** en vez de anidarse.
- `Promise.all([...])` espera varias promesas concurrentemente y falla si falla una.
- `async`/`await` es azúcar sintáctica sobre promesas: el código se lee de arriba hacia abajo, pero sigue siendo asíncrono por debajo. Es la misma idea que vamos a ver con las corrutinas de Python.

```js
cuentaA.puedeExtraer(50)
  .then(puede => puede ? cuentaA.extraer(50) : Promise.reject('sin fondos'))
  .then(() => cuentaB.depositar(50))
  .catch(err => console.log(err));
```

## 6. El event loop a mano en Python: sockets no bloqueantes + selector + callbacks

Volvamos al crawler. Con lo visto, la alternativa a un thread por conexión es armar nuestro propio event loop: **sockets no bloqueantes**, un **selector** que avisa cuál está listo y **callbacks**.

```py
from selectors import DefaultSelector, EVENT_WRITE

selector = DefaultSelector()

sock = socket.socket()
sock.setblocking(False)                 # las operaciones vuelven enseguida
try:
    sock.connect(('bla.com', 80))       # lanza BlockingIOError aunque todo vaya bien
except BlockingIOError:
    pass                                # significa "empecé, todavía no terminé"

def connected():                        # el callback: qué hacer cuando conecte
    selector.unregister(sock.fileno())
    print('connected!')

# "avisame cuando este socket se pueda escribir, y llamá a connected"
selector.register(sock.fileno(), EVENT_WRITE, connected)

def loop():                             # el event loop
    while True:
        events = selector.select()      # duerme hasta que algún socket esté listo
        for event_key, event_mask in events:
            callback = event_key.data
            callback()
```

Paso a paso:
1. **Socket no bloqueante**: `setblocking(False)` hace que las operaciones vuelvan enseguida en vez de frenar al thread. Por eso `connect` lanza `BlockingIOError` (errno `EINPROGRESS`) aunque esté funcionando: no es un error real, es un "ya arranqué el handshake, seguí con lo tuyo", y se ignora con `pass`. Ahora no sabemos cuándo va a terminar: entra el no determinismo.
2. **Registro en el selector**: se registra el socket, el evento que interesa y el callback a llamar. `EVENT_WRITE` significa "listo para escribir", que para un socket TCP ocurre cuando termina el handshake: en la práctica, "conexión establecida". `EVENT_READ` significa "hay datos para leer".
3. **El loop**: `selector.select()` es, por dentro, `epoll_wait()` en Linux. El thread se bloquea ahí **sin gastar CPU**. El kernel sabe por hardware cuándo llegan datos, marca ese descriptor como listo y despierta a `select`, que devuelve la lista de eventos listos. El loop ejecuta el callback de cada uno.

**Todo esto corre en un solo thread.** Si hay 1000 sockets conectando a la vez, el mismo loop los atiende a todos, uno por uno, a medida que cada uno avisa que está listo. Nunca hay dos cosas ejecutándose en el mismo instante: es **concurrencia** (superponer esperas de I/O), no paralelismo. Si el trabajo fuera de CPU, este esquema no ayudaría.

**El problema**: la lógica de `fetch` (conectar → enviar → leer → parsear), que antes se leía de arriba hacia abajo, queda **partida en callbacks**, y el estado (qué socket, qué llevo leído) hay que guardarlo **afuera**, en variables globales o en objetos. Es el mismo problema que el CPS en Node. Lo que queremos es escribir el código como si fuera secuencial, pero que pueda **pausarse** en cada espera. Para eso necesitamos funciones que se puedan pausar.

## 7. Generadores: funciones que se pueden pausar

- Un **iterador** es un objeto que permite recorrer una colección un elemento a la vez, bajo demanda (implementa `__next__()`). El `for`, las comprensiones y `list()` usan este protocolo.
- Un **generador** es una forma de construir iteradores: una función que, en vez de devolver un único valor, **produce una secuencia de valores**. Se escribe con `yield`.

```py
def cuenta_regresiva(numero):
    while numero > 0:
        yield numero
        numero -= 1

for numero in cuenta_regresiva(5):
    print(numero)

# Imprime: 5 4 3 2 1
```

`yield` entrega un valor a quien pidió el siguiente (con `next()`) y **pausa la función congelando su estado** hasta que se vuelva a pedir otro. `return`, en cambio, termina la función y borra su estado.

**Llamar a una función con `yield` no ejecuta nada.** `cuenta_regresiva(5)` solo crea el **objeto generador**: una "cápsula" con la ejecución congelada en el punto de partida, esperando el primer `next()`. (Esto mismo va a pasar con las corrutinas.)

¿Cómo se conserva el estado? En una función común, al terminar, Python destruye su *stack frame* (variables locales, posición actual). En un generador, ese frame vive en el **heap** y el generador lo retiene. Paso a paso:

1. `cuenta_regresiva(5)` crea el generador: frame nuevo con `numero=5`, todavía sin ejecutar nada.
2. El `for` hace `next(gen)`: entra al frame, el `while` se cumple, llega a `yield numero`, devuelve `5` y **congela el frame ahí**.
3. El `for` recibe el `5` y ejecuta `print(5)`.
4. El `for` pide el siguiente con `next(gen)`: Python **no vuelve a entrar por arriba**, retoma justo **después** del `yield`. Ejecuta `numero -= 1` (mismo frame, misma variable), vuelve al `while`, llega a `yield` y devuelve `4`.
5. Así hasta `numero=0`: el `while` no entra, la función llega a su fin y se lanza `StopIteration`, que el `for` capta para terminar.

La variable `numero` **nunca sale de la función**: vive en su frame, que persiste entre llamadas a `next()`, como una función pausada con un señalador en el punto donde quedó.

## 8. Corrutinas

Una **corrutina** es como una subrutina (una función común), con una diferencia: la salida de una subrutina **termina** su ejecución, mientras que una corrutina puede **suspenderse, cediendo el control a otra**, hasta que se le indique que retome.

Los generadores son un caso particular de esto. Lo que les falta para ser corrutinas completas es **recibir valores al retomarse**:
- En un **generador**, `yield` pausa y entrega un valor; `next()` lo retoma.
- En una **corrutina** basada en generadores, además se la retoma con `send(valor)`, y el `yield` "devuelve" ese valor adentro de la función. Así se le puede pasar, por ejemplo, el resultado de la I/O que estaba esperando.

Otra diferencia: un generador, al ceder, siempre le devuelve el control **a quien lo llamó** (está pensado para producir valores para un `for`). Una corrutina cede el control a un planificador que decide **qué corrutina sigue**.

### Cómo se construyen corrutinas sobre un event loop
Para reemplazar callbacks por corrutinas hacen falta tres piezas más, además del event loop:

- **Future**: un objeto que representa **un resultado que todavía no existe** (la respuesta de un socket, por ejemplo). Cuando alguien lo resuelve con `set_result(valor)`, avisa a los callbacks que tenga registrados.
- **Corrutina**: la función con la lógica secuencial. Cada vez que necesita esperar algo, hace `yield future` y queda pausada.
- **Task**: el objeto que **maneja una corrutina**: la arranca, y cada vez que el future que la corrutina está esperando se resuelve, la retoma con ese resultado.

```py
class Task:
    def __init__(self, coro):
        self.coro = coro
        f = Future()
        f.set_result(None)          # un future ya resuelto, para arrancar
        self.step(f)

    def step(self, future):
        try:
            # retoma la corrutina pasándole el resultado; corre hasta el próximo yield
            next_future = self.coro.send(future.result())
        except StopIteration:
            return                  # la corrutina terminó
        # cuando ese future se resuelva, volver a llamar a step
        next_future.add_done_callback(self.step)

def fetch(url):                     # la corrutina: se lee de arriba hacia abajo
    sock = yield conectar(url)      # conectar() devuelve un future y fetch se pausa
    respuesta = yield leer(sock)    # idem
    parse_response(respuesta)
```

El ciclo completo:
1. La corrutina hace `yield future` y se pausa.
2. La Task le engancha `step` al future con `add_done_callback`.
3. El selector detecta que el socket está listo y el callback resuelve el future (`set_result`).
4. `step` hace `coro.send(future.result())` y la corrutina sigue hasta el próximo `yield`.
5. Cuando no hay más `yield`, se lanza `StopIteration` y la Task termina.

Los callbacks no desaparecen: siguen estando, pero **escondidos** dentro de Task y Future. El código que escribimos queda lineal.

### `async`/`await`
Python trae todo esto armado en **asyncio**, con sintaxis propia:

| Implementación propia | asyncio |
|---|---|
| Función generadora | `async def` |
| `yield future` / `yield from future` | `await` |
| Task propia | `asyncio.create_task` |
| Loop propio | `asyncio.run` |

Así, el `fetch` del crawler queda:

```py
async def fetch(url):
    reader, writer = await asyncio.open_connection('bla.com', 80)   # se pausa mientras conecta
    writer.write(f'GET {url} HTTP/1.0\r\nHost: bla.com\r\n\r\n'.encode())
    respuesta = await reader.read()                                 # se pausa mientras llegan datos
    parse_response(respuesta)
```

Es casi idéntico a la versión bloqueante del principio, pero cada `await` es un punto donde la corrutina **cede el control** y el loop puede atender a otras.

### Ventajas y desventajas de pasar de callbacks a corrutinas

| ✅ Ventajas | ❌ Desventajas |
|---|---|
| El código se lee de arriba hacia abajo, como el secuencial | **No hay paralelismo**: un solo thread, no sirve para CPU bound |
| El estado queda en variables locales, no repartido en callbacks | Un llamado bloqueante (`time.sleep`, un `recv` común) **congela a todas** las corrutinas |
| Los errores se manejan con `try/except` normal | `async` se contagia como el CPS: quien hace `await` tiene que ser `async` también |
| Muy livianas (~3 KB contra ~50 KB de un thread) y el cambio de contexto no pasa por el SO | Hacen falta librerías async (un driver bloqueante no sirve) |
| Entre dos `await` nadie interrumpe: ese tramo no necesita locks | Si una operación lee, hace `await` y después escribe, otra corrutina puede meterse en el medio: igual puede haber carreras |

## 9. asyncio en la práctica

### Sin corrutinas
Tres tareas, cada una con tres esperas de 1 segundo:

```py
import time

def io():
    time.sleep(1)
    print('1')
    time.sleep(1)
    print('2')
    time.sleep(1)
    print('3')

def main(tareas):
    for tarea in tareas:
        io()

if __name__ == '__main__':
    tiempo = time.perf_counter()
    main(range(3))
    print(f'Tiempo total: {time.perf_counter() - tiempo:0.2f} segundos')

# Imprime 1 2 3 1 2 3 1 2 3 — Tiempo total: 9.01 segundos
```

Cada tarea empieza recién cuando termina la anterior.

### Con corrutinas

```py
import time
import asyncio

async def io():                      # async def: es una corrutina
    await asyncio.sleep(1)           # cede el control mientras espera
    print(1)
    await asyncio.sleep(1)
    print(2)
    await asyncio.sleep(1)
    print(3)

async def main():
    await asyncio.gather(io(), io(), io())

if __name__ == '__main__':
    tiempo = time.perf_counter()
    asyncio.run(main())
    print(f'Tiempo total: {time.perf_counter() - tiempo:0.2f} segundos')

# Imprime 1 1 1 2 2 2 3 3 3 — Tiempo total: 3.00 segundos
```

`asyncio.gather(io(), io(), io())` lanza las tres corrutinas al event loop **concurrentemente** y espera a que terminen las tres. Traza:
1. Arrancan las 3 casi a la vez (t=0).
2. Cada una llega a `await asyncio.sleep(1)` y se **pausa**, devolviendo el control al loop con un "avisame en 1 segundo".
3. A t≈1 el loop las despierta, cada una imprime `1` y vuelve a dormir.
4. A t≈2 imprimen `2`; a t≈3 imprimen `3` y terminan.

Las tres comparten un solo thread pero **superponen sus esperas**. No hay paralelismo (la ejecución del código Python es secuencial), pero como el trabajo es solo esperar, se pueden esperar las tres cosas a la vez. Si en vez de `sleep` fuera un cálculo pesado, no ganaríamos nada.

Es como una **simultánea de ajedrez**: una persona juega contra varias, hace un movimiento en un tablero y, en vez de esperar la respuesta, pasa al siguiente. Las partidas avanzan concurrentemente y terminan antes. **Hay concurrencia, no paralelismo.**

### Cómo ejecutar una corrutina
Igual que con los generadores, **llamar a una función `async def` no ejecuta su cuerpo**: devuelve un objeto corrutina congelado, listo para arrancar. Alguien tiene que planificarlo:

| Forma | Qué hace | Cuándo usarla |
|---|---|---|
| `asyncio.run(coro)` | Crea el event loop y corre **una** corrutina de punta a punta | Punto de entrada del programa, una sola vez, en el `main` |
| `await coro` | Ejecuta la corrutina y **espera su resultado antes de seguir**. Es el punto donde la corrutina actual **cede el control** al loop mientras tanto | Cuando necesitás el resultado para continuar. Dos `await` seguidos corren **en secuencia** |
| `asyncio.create_task(coro)` | Envuelve la corrutina en una **Task** y la manda al loop **en segundo plano**, sin esperarla. Es lo que permite tener **varias corrutinas en vuelo a la vez** | Cuando querés que arranque ya y seguir con otra cosa (por ejemplo, registrar una métrica sin demorar la respuesta). El resultado se espera después con `await task` |
| `asyncio.gather(c1, c2, ...)` | Hace un `create_task` por cada una, las corre concurrentemente y devuelve los resultados **en el orden en que se pasaron**, no en el que terminaron | Varias consultas independientes de las que querés todos los resultados |
| `asyncio.TaskGroup()` | Con `async with`: las tareas creadas adentro se esperan todas al salir del bloque, y **si una falla, cancela a las demás** | Concurrencia estructurada: tareas que forman una sola unidad de trabajo |

### `gather` vs. `TaskGroup`
- **`gather`**: "ejecutá estas cosas concurrentemente y dame sus resultados". Si una falla, la excepción le llega a quien hizo el `await`, pero **las otras siguen corriendo** (no se cancelan). Con `return_exceptions=True`, los errores vuelven como un resultado más de la lista y se pueden manejar uno por uno.
- **`TaskGroup`**: "estas tareas forman juntas una unidad de trabajo; si una falla, cancelá correctamente las demás". Ojo: cancelar **no es deshacer**. Lo que las tareas hermanas ya hicieron queda hecho; no es una transacción con rollback.

| Característica | `asyncio.gather()` | `asyncio.TaskGroup` |
|---|---|---|
| Ejecutar cosas concurrentemente | ✅ | ✅ |
| Obtener resultados | Directo, en una lista | Desde cada `Task` (`task.result()`) |
| Manejo de errores | Flexible | Estructurado |
| Cancela hermanas cuando una falla | ❌ No por defecto | ✅ |
| Concurrencia estructurada | ❌ | ✅ |
| Equivalente en JS | `Promise.all` | — |
| Uso típico | "Necesito estos resultados" | "Estas tareas forman un trabajo" |

**Reglas de la concurrencia estructurada**:
- **Duración limitada**: las tareas no pueden sobrevivir al bloque que las creó.
- **Jerarquía padre-hijo**: la tarea padre espera a que terminen todas las hijas.
- **Propagación**: si una hija falla o se cancela, se detienen las hermanas.

### Limitar la concurrencia: `asyncio.Semaphore`
Lanzar todo junto puede saturar al servicio que estamos consultando. Un semáforo acota cuántas corrutinas pueden estar en una sección a la vez:

```py
limite = asyncio.Semaphore(4)

async def consultar(linea):
    async with limite:              # si ya hay 4 adentro, espera un permiso
        return await pedir_linea(linea)
```

Las consultas extra esperan su turno: se acota la carga, a cambio de que el tiempo total pueda crecer.

## 10. Código bloqueante dentro de una corrutina

Una corrutina solo cede el control en sus `await`. Si llama a algo **bloqueante** (`time.sleep`, un `recv` de socket común, un driver de base de datos sincrónico) o hace un **cálculo largo**, no hay ningún `await` donde ceder, y **el único thread queda ocupado**: el loop no puede atender a ninguna otra corrutina mientras tanto.

```py
import asyncio, time

async def bloqueante():
    time.sleep(2)               # bloquea el thread: el loop queda congelado 2 s

async def cooperativa():
    await asyncio.sleep(2)      # cede el control: el loop atiende otras mientras espera

async def main():
    inicio = time.perf_counter()
    await asyncio.gather(bloqueante(), bloqueante())
    print(time.perf_counter() - inicio)     # ~4 s: una detrás de la otra

    inicio = time.perf_counter()
    await asyncio.gather(cooperativa(), cooperativa())
    print(time.perf_counter() - inicio)     # ~2 s: las esperas se solapan

asyncio.run(main())
```

Que la función esté declarada con `async def` **no cambia nada**: lo que importa es si lo que llama cede o bloquea. Soluciones:

```py
async def main():
    loop = asyncio.get_running_loop()

    # 1. Usar la versión async de la operación, si existe
    await asyncio.sleep(1)                  # en vez de time.sleep(1)

    # 2. Mandar lo bloqueante a otro thread del pool, y esperar su resultado con await
    datos = await loop.run_in_executor(None, consulta_bloqueante, 'id-42')
    #       (forma moderna equivalente: await asyncio.to_thread(consulta_bloqueante, 'id-42'))

    # 3. Ponerle un límite de tiempo a una corrutina
    try:
        await asyncio.wait_for(consulta_lenta(), timeout=1.0)
    except TimeoutError:
        print('tardó demasiado, se canceló')
```

Mandar el trabajo a otro thread libera al loop. Para un cálculo CPU bound en Python, ese thread sigue limitado por el GIL; si hace falta paralelismo real de CPU, se usa un pool de **procesos** (`concurrent.futures.ProcessPoolExecutor`).

## 11. Corrutinas vs. threads

| | Threads | Corrutinas |
|---|---|---|
| Multitarea | **Apropiativa**: el planificador del SO asigna intervalos de CPU y desaloja en cualquier punto | **Cooperativa**: cada corrutina cede el control en su `await`, cuando está esperando |
| Quién decide qué corre | El scheduler del SO | El event loop (el SO solo planifica el thread del loop) |
| Paralelismo | Puede haberlo | No: un solo thread |
| Condiciones de carrera | En cualquier punto: hacen falta locks | Solo entre dos `await` puede cambiar el estado |
| Memoria | ~50 KB | ~3 KB |
| Cambio de contexto | Llamada al sistema operativo | Dentro de la aplicación, sin syscalls |
| Sirven para | CPU bound (si hay paralelismo) e IO bound | IO bound |

Internamente, ante un `await`:
1. Se pausa la corrutina.
2. Se le devuelve el control al event loop con un "avisame cuando esté listo".
3. El loop queda libre para atender otras corrutinas o esperar eventos.
4. Cuando la condición se cumple, el loop la retoma justo después del `await` (como `next()` en los generadores).

Por eso las corrutinas son ideales para **I/O** y no para CPU: no hay un planificador que desaloje a una corrutina que se pasa de largo calculando.

### Fibers
Otra variante de tarea suspendible (por ejemplo, las **fibers** de Ruby): una tarea puede suspenderse y continuar desde donde quedó, y el runtime ejecuta otra en el mismo thread durante la espera. Igual que con las corrutinas, una llamada bloqueante dentro de la fiber ocupa el thread si el runtime no la delega.

## 12. Laboratorio "Cuando Viene"

El servicio **Cuando Viene** consulta una parada y después pide el detalle de sus líneas; **Monitoreo** consulta el estado de los servicios y lo publica por WebSocket. [Consigna](https://github.com/arquitecturas-concurrentes/iasc-python-cuando-viene).

| Qué pide | Concepto | Cómo comprobarlo |
|---|---|---|
| Demorar algunos pedidos de Paradas | Espera no bloqueante con `await asyncio.sleep` | Mientras un pedido espera, `/health` sigue respondiendo |
| Obtener la parada en `arrival_times` | Hacer `await` de la corrutina para obtener su resultado | La lógica recibe los datos y no un objeto corrutina |
| Consultar varias líneas y tolerar fallos | Ejecutar consultas independientes juntas y manejar el error de cada una | Si una línea falla, las demás igual salen (`gather(..., return_exceptions=True)` o manejar el error dentro de cada tarea) |
| Monitorear tres servicios por WebSocket | Consultas juntas, espera entre rondas y cancelación al cerrar la conexión | Con dos pestañas, cerrar una no corta la otra |
| Registrar una métrica sin demorar la respuesta | Trabajo en segundo plano (`create_task`) | La respuesta llega antes de que termine la métrica |
| Limitar el número de consultas | `asyncio.Semaphore(4)` | Nunca hay más de 4 consultas en curso |

La decisión central: la consulta de la parada **tiene que terminar antes** de conocer sus líneas (dependencia: van con `await` en secuencia), pero las consultas por línea **pueden solaparse** (independientes: van con `gather` o `TaskGroup`).

## Preguntas típicas de parcial

- **¿El SO decide qué corrutina retomar?** No: el SO planifica el **thread** del event loop y avisa que la I/O está lista; el event loop elige qué corrutina reanudar.
- **¿Puede haber condiciones de carrera con un solo thread?** Sí. Si A lee un contador, hace `await` antes de escribir, y B lee el mismo valor y lo actualiza, al retomar A pisa el cambio de B. Las carreras aparecen **entre dos `await`** (o entre dos callbacks en el event loop).
- **¿`async def` alcanza para no bloquear?** No: un `time.sleep` o un cálculo pesado dentro de una corrutina bloquea todo el loop.
- **¿Qué tarda menos, dos consultas de 1 s y 2 s en secuencia o juntas?** Idealmente ~3 s en secuencia y ~2 s solapadas.
- **¿Qué ganás con un semáforo?** Acotás la carga sobre el servicio; las consultas extra esperan un permiso y el tiempo total puede crecer.
